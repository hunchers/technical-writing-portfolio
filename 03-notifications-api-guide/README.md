# API уведомлений

Учебно-практическая документация вымышленного REST API. Она показывает
подход к описанию интеграции: от первого запроса до обработки ошибок и
получения статуса отправки.

## Назначение

API позволяет внешней системе отправлять пользователям уведомления и
отслеживать их доставку. Поддерживаются каналы `email` и `sms`.

Базовый URL:

```text
https://api.example.test/v1
```

Все примеры используют тестовый адрес и демонстрационные данные.

## Быстрый старт

1. Получите API-ключ в настройках интеграции.
2. Передавайте ключ в заголовке `Authorization`.
3. Отправьте запрос на создание уведомления.
4. Сохраните идентификатор уведомления из ответа.
5. Запросите статус доставки по идентификатору.

```bash
curl --request POST 'https://api.example.test/v1/notifications' \
  --header 'Authorization: Bearer demo_api_key' \
  --header 'Content-Type: application/json' \
  --data '{
    "channel": "email",
    "recipient": "user@example.com",
    "subject": "Подтверждение записи",
    "message": "Ваша запись подтверждена."
  }'
```

Успешный запрос возвращает код `201 Created` и объект уведомления:

```json
{
  "id": "ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6",
  "status": "queued",
  "created_at": "2026-09-12T10:15:30Z"
}
```

## Аутентификация

Передавайте API-ключ в каждом запросе:

```text
Authorization: Bearer <api_key>
```

Ключ даёт доступ к данным интеграции. Храните его в переменных окружения
или защищённом хранилище секретов. Не добавляйте ключ в исходный код,
скриншоты и публичные журналы.

Если ключ отсутствует или недействителен, API возвращает `401 Unauthorized`.

## Формат данных

API принимает и возвращает JSON. Дата и время указываются в UTC в формате
ISO 8601, например `2026-09-12T10:15:30Z`.

### Статусы уведомления

| Статус | Значение |
| --- | --- |
| `queued` | Запрос принят и ожидает отправки. |
| `sent` | Уведомление передано провайдеру канала. |
| `delivered` | Провайдер подтвердил доставку. |
| `failed` | Отправка завершилась ошибкой. Причина доступна в поле `error`. |
| `canceled` | Отправка отменена до передачи провайдеру. |

## Методы API

### Создать уведомление

`POST /notifications`

Создаёт одно уведомление. Метод возвращает объект со статусом `queued`.

#### Параметры тела запроса

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `channel` | string | Да | Канал доставки: `email` или `sms`. |
| `recipient` | string | Да | Email-адрес для `email` или номер в формате E.164 для `sms`. |
| `message` | string | Да | Текст уведомления, от 1 до 1 000 символов. |
| `subject` | string | Для `email` | Тема письма, от 1 до 200 символов. |
| `client_reference` | string | Нет | Внешний идентификатор для сопоставления с записью в системе клиента. |

#### Пример запроса

```bash
curl --request POST 'https://api.example.test/v1/notifications' \
  --header 'Authorization: Bearer demo_api_key' \
  --header 'Content-Type: application/json' \
  --data '{
    "channel": "sms",
    "recipient": "+79990000000",
    "message": "Код подтверждения: 482913",
    "client_reference": "order-8431"
  }'
```

#### Ответ `201 Created`

```json
{
  "id": "ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6",
  "channel": "sms",
  "recipient": "+79990000000",
  "status": "queued",
  "client_reference": "order-8431",
  "created_at": "2026-09-12T10:15:30Z"
}
```

Если поле `recipient` не соответствует выбранному каналу, API возвращает
ошибку валидации `422 Unprocessable Entity`.

### Получить уведомление

`GET /notifications/{notification_id}`

Возвращает текущее состояние уведомления и информацию об ошибке, если
доставка завершилась со статусом `failed`.

```bash
curl --request GET \
  'https://api.example.test/v1/notifications/ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6' \
  --header 'Authorization: Bearer demo_api_key'
```

#### Ответ `200 OK`

```json
{
  "id": "ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6",
  "channel": "sms",
  "recipient": "+79990000000",
  "status": "delivered",
  "created_at": "2026-09-12T10:15:30Z",
  "delivered_at": "2026-09-12T10:15:34Z"
}
```

Если уведомление с таким идентификатором не найдено, API возвращает
`404 Not Found`.

### Получить список уведомлений

`GET /notifications`

Возвращает уведомления текущей интеграции. Результаты отсортированы по
времени создания от новых к старым.

| Параметр | Тип | Описание |
| --- | --- | --- |
| `status` | string | Фильтр по статусу: `queued`, `sent`, `delivered`, `failed`, `canceled`. |
| `limit` | integer | Количество записей в ответе: от 1 до 100. Значение по умолчанию — 20. |
| `cursor` | string | Курсор следующей страницы из поля `next_cursor`. |

```bash
curl --request GET \
  'https://api.example.test/v1/notifications?status=failed&limit=20' \
  --header 'Authorization: Bearer demo_api_key'
```

#### Ответ `200 OK`

```json
{
  "data": [
    {
      "id": "ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6",
      "channel": "email",
      "recipient": "user@example.com",
      "status": "failed",
      "error": {
        "code": "recipient_unreachable",
        "message": "Адрес получателя недоступен."
      },
      "created_at": "2026-09-12T10:15:30Z"
    }
  ],
  "next_cursor": null
}
```

### Отменить уведомление

`POST /notifications/{notification_id}/cancel`

Отменяет уведомление в статусе `queued`. Для уже отправленного или
доставленного уведомления API возвращает `409 Conflict`.

```bash
curl --request POST \
  'https://api.example.test/v1/notifications/ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6/cancel' \
  --header 'Authorization: Bearer demo_api_key'
```

#### Ответ `200 OK`

```json
{
  "id": "ntf_01HZX4Q2K8M6Y7P9A3B5C1D4E6",
  "status": "canceled",
  "canceled_at": "2026-09-12T10:16:02Z"
}
```

## Ошибки и действия клиента

| Код | Причина | Действие |
| --- | --- | --- |
| `400 Bad Request` | Запрос содержит некорректный JSON или параметр. | Проверьте формат тела запроса и значения полей. |
| `401 Unauthorized` | API-ключ отсутствует, истёк или отозван. | Проверьте заголовок `Authorization` и выпустите новый ключ при необходимости. |
| `404 Not Found` | Ресурс не существует или недоступен этой интеграции. | Проверьте идентификатор и используемый API-ключ. |
| `409 Conflict` | Операция невозможна в текущем статусе объекта. | Получите актуальный статус уведомления и повторите допустимое действие. |
| `422 Unprocessable Entity` | JSON корректен, однако нарушены правила валидации. | Исправьте поля, перечисленные в объекте `details`. |
| `429 Too Many Requests` | Превышен лимит запросов. | Дождитесь времени из заголовка `Retry-After`, затем повторите запрос. |
| `500 Internal Server Error` | Внутренняя ошибка сервиса. | Повторите запрос с увеличивающейся паузой. Если ошибка сохраняется — передайте в поддержку `request_id`. |

### Формат ошибки

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте параметры запроса.",
    "details": [
      {
        "field": "recipient",
        "message": "Для SMS используйте номер в формате E.164."
      }
    ]
  },
  "request_id": "req_01HZX5F5B7J2T4V6W8X0Y3Z9A1"
}
```

## Ограничения и повторные попытки

- Лимит API — 60 запросов в минуту на один API-ключ.
- Размер тела запроса — до 64 КБ.
- Для ошибок `429` и `500` используйте повторные попытки с увеличивающейся
  паузой.
- Перед повторной отправкой уведомления запросите его статус: так можно
  избежать повторной доставки пользователю.

## Что приложить к обращению в поддержку

Для разбора ошибки подготовьте:

- `request_id` из ответа API;
- HTTP-код и тело ответа без API-ключа;
- время запроса в UTC;
- используемый endpoint и HTTP-метод;
- идентификатор уведомления, если он был создан;
- пример запроса без персональных данных и секретов.
