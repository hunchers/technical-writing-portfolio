# 2. Модель доступа

## Задача

В базе знаний нужно было совместить две задачи:

-   дать сотруднику необходимый для работы доступ;
-   не создавать полноценный оплачиваемый аккаунт для каждого
    сотрудника.

Разные подразделения также должны были самостоятельно управлять своей
документацией.

## Основная модель

Использовались два основных типа аккаунтов:

-   **оплачиваемые** — для сотрудников, которым требовалась
    полноценная работа с документацией;
-   **гостевые** — преимущественно для сотрудников, которым было
    достаточно читать материалы.

Масштаб составлял примерно:

**30 оплачиваемых аккаунтов + до 50 гостевых.**

Такой подход позволял предоставить необходимый доступ большему числу
сотрудников без оплаты полноценного аккаунта для каждого.

## Группы

Оплачиваемые аккаунты объединялись в группы.

Группы проектировались с учётом реальной структуры подразделений.

Если внутри отдела не требовалось различать права по ролям,
использовалась одна группа:

``` mermaid
flowchart LR
    HR["Сотрудник HR"] --> G["Группа HR"]
    G --> P["Права HR-домена"]
```

В подразделениях с большим количеством ролей права разделялись
детальнее:

``` mermaid
flowchart LR
    D["Development"] --> DEV["Developer"]
    D --> QA["QA"]
    D --> BSA["BSA"]
    D --> PM["PM"]
    DEV --> R1["Нужные права"]
    QA --> R2["Нужные права"]
    BSA --> R3["Нужные права"]
    PM --> R4["Нужные права"]
```

Также существовали группы с расширенными административными правами.

## Онбординг нового сотрудника

Доступ определялся ролью сотрудника.

``` mermaid
flowchart TB
    A["Новый сотрудник"] --> B["Определить роль"]
    B --> C["Выбрать группу"]
    C --> D["Добавить сотрудника"]
    D --> E["Получить права группы"]
    E --> F["Чтение / комментирование / редактирование"]
```

Если выходил новый разработчик, его добавляли в соответствующую группу.
После этого он получал доступ к нужным разделам с необходимым уровнем
прав.

## Уровни доступа

В зависимости от роли и раздела использовались:

-   чтение;
-   комментирование;
-   редактирование.

В `Main` права в основном были рассчитаны на чтение и комментирование.

В `Domain` сотрудники соответствующего подразделения могли получать
права на редактирование и самостоятельно поддерживать свою документацию.

## Restricted-доступ

Внутри доменов существовали отдельные закрытые пространства.

Например, в HR был закрытый раздел с чувствительной информацией о
сотрудниках, доступный только HR и соответствующим руководителям.

При необходимости для отдельных страниц использовался
`Restricted`-доступ.

Иерархическая структура позволяла создавать такие исключения внутри
домена без перестройки всей системы прав.

## Моя зона ответственности

Я самостоятельно проектировала и настраивала модель доступа:

-   определяла структуру групп;
-   создавала группы;
-   назначала права;
-   первоначально добавляла сотрудников;
-   определяла соответствие ролей и доступов;
-   настраивала ограничения для отдельных разделов.

После первоначальной настройки дальнейшая выдача доступов к рабочим
инструментам была зоной ответственности системного администратора.

## Связь с HR

В процессе работы с доступами мы вместе с HR проработали необходимые
доступы для разных ролей.

Так появились **карточки ролей**:

``` text
Роль
  ↓
Необходимые системы и пространства
  ↓
Необходимый уровень доступа
```

Это стало практическим инструментом онбординга: HR мог определить набор
доступов исходя из роли нового сотрудника и использовать его при
оформлении доступа.

## Результат

Модель позволила:

-   сократить количество оплачиваемых аккаунтов;
-   управлять доступом через группы и роли;
-   разделять чтение, комментирование и редактирование;
-   дать подразделениям возможность самостоятельно поддерживать свои
    пространства;
-   создавать закрытые области внутри доменов;
-   использовать структуру доступов в процессе онбординга.

> **Главный принцип модели:** доступ определяется ролью, зоной
> ответственности и типом информации.
